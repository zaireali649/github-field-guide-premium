GitHub Field Guide

Every word you will hear in your first month with Git and GitHub, explained once, plainly, in the order you will actually meet them. Then the full path from a folder on your laptop to a live website.

Chapter 01

Git is not GitHub

The distinction everything else rests on

  • Git runs on your machine
  • GitHub runs on the web
  • You can use Git without GitHub
  • You cannot use GitHub without Git

Git is a program installed on your computer. It watches a folder and lets you save named snapshots of it over time, so you can look back, compare, and undo. It works entirely offline.

GitHub is a website that holds a copy of that folder and its history online, so other people (and other machines) can reach it. On top of storage it adds review tools, a to-do list, and automation. GitHub is one of several such services; GitLab and Bitbucket do the same job.

One more line worth memorising: putting code on GitHub does not make a website. It stores the code. Something else has to build it and serve it. That is chapter three.

  1. 01

    Repository

    A project folder Git is tracking. Usually shortened to repo. One repo, one project.

  2. 02

    Local and remote

    Local is the copy on your computer. Remote is the copy on GitHub. They only match after you sync them.

  3. 03

    Clone

    Download a complete copy of a remote repo, history and all, already wired to push back to it.

    git clone https://github.com/you/site.git
  4. 04

    README

    A Markdown file GitHub shows on the repo home page. Write what the project is and how to run it.

Chapter 02

Saving work, sharing work

The daily loop

Edit. Commit. Push.

A commit is a saved snapshot with a message saying why. Commits pile up into history. A branch is a separate line of commits so you can try something without disturbing main, the branch everyone treats as the stable version.

Push uploads your commits to GitHub. Pull downloads commits others pushed. A diff is the line-by-line view of what changed, which you read before committing and before approving anyone else’s work.

your-site
# start a branch for the change
git switch -c fix-header

# ...edit files...
git diff                          # read what you changed
git add .
git commit -m "Fix header alignment on mobile"

# share it
git push -u origin fix-header
Commit
Snapshot plus message. Small and frequent beats large and rare.
Branch
Parallel line of work. Cheap to make, easy to throw away.
main
The default branch. Older repos call it master. Just a name.
Push / Pull
Up to the remote, down from the remote. Pull before you start; push when you finish.
Diff
Removed lines start with a minus, added lines with a plus.

Chapter 02 · continued

Working with other people

Where each thing happens

  • Merge: Git, on any machine
  • Conflict: Git, on your machine
  • Pull request: GitHub
  • Issue: GitHub
  • Fork: GitHub

A pull request (PR) is GitHub’s way of saying “I would like these commits from my branch to go into main. Please look.” It shows the diff, hosts the discussion, and has a Merge button. It is a GitHub feature, not a Git command.

Merge combines one branch into another. When two branches changed the same lines, Git stops and reports a merge conflict. It marks the spot in the file; you pick the version you want, delete the markers, and commit. Normal, not a disaster.

An issue is a ticket: a bug, a task, an idea. A fork is your own copy of someone else’s repo on GitHub, so you can change it and then offer the changes back through a PR.

index.html (conflicted)
<h1>
<<<<<<< HEAD
  Welcome to my site
=======
  Welcome to our site
>>>>>>> fix-header
</h1>

# keep one line, delete the three marker lines, then:
git add index.html
git commit

Chapter 03

From laptop to live

Three places, three jobs. Your laptop is where you write and test. GitHub is where the code is stored and reviewed. A host such as Vercel watches the GitHub repo, builds the site whenever main changes, and serves the result at a public address. GitHub never serves your site; the host does.

  1. 1

    Build locally

    Make the folder a repo and confirm the site runs on your machine first.

    git init
npm install
npm run dev
  2. 2

    Commit and push to GitHub

    Create an empty repo on github.com, then connect and upload.

    git add .
git commit -m "Initial site"
git remote add origin https://github.com/you/site.git
git push -u origin main
  3. 3

    Connect the repo to Vercel

    In Vercel, choose Import Project and pick the GitHub repo. Vercel reads the framework, runs the build command, and publishes the output. You do not upload files by hand. 

    Build command:  npm run build
Output folder:  dist
  4. 4

    Every push deploys

    Pushes to main become the production deployment. Pushes to any other branch or PR get a preview URL so you can check before it goes live.

  5. 5

    Point a domain at it

    Buy a domain from a registrar, add it in Vercel, and set the DNS records Vercel shows you. HTTPS is issued automatically.

Where GitHub Actions fits

GitHub Actions runs scripts inside GitHub when something happens, most often running tests on every push or PR. It can also deploy, but with Vercel you rarely need it for that: Vercel deploys by watching the repo itself. Use Actions to catch broken builds before they reach the host. 

# .github/workflows/ci.yml
on: [push, pull_request]
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm ci
      - run: npm run build
